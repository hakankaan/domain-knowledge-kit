# ADR-0006 — Artifact provenance via a committed lock file

**Status:** Accepted  
**Date:** 2026-07-27  
**Deciders:** Kaan Akın

## Context

DKK installs files into other people's repositories — hook scripts, skills, subagents, slash commands, prompt files — and `dkk update` refreshes them on every release. Until now the refresh decided what to do from a content comparison alone: if the file on disk differed from the bundled template, it was listed as `~ replace` and handed to the installer with `force: true`.

That single classification covers two situations with opposite correct answers:

1. **The file is the previous release's copy.** Overwriting is the entire point of an upgrade.
2. **Somebody edited it.** Overwriting destroys work that was deliberately done.

A content comparison cannot distinguish them, because both simply "differ from the template". A downstream user reported losing the same local patch twice: a fix to `stop-validate.mjs` that they had to carry because upstream's version wedged their sessions. Both times `dkk update` printed one indistinguishable `~ replace` line and silently reverted it.

Three adjacent problems shared the same root — the tool acting on an assumption it had no evidence for:

- **The confirmation prompt showed paths, not content.** There was no way to see what was about to be lost without opening another terminal and running `git diff`. And the settings-merge warnings (`mixed DKK/user commands left intact`) printed *after* the writes, so the one piece of decision-relevant information arrived too late to inform the decision.
- **Case-only renames never reached the repository.** 0.7.0 renamed `.github/skills/dkk-*/skill.md` → `SKILL.md`. On macOS and Windows `core.ignorecase=true` means git matches the new working-tree entry against the old index entry and reports no change at all. The rename landed on disk, never in a commit — so Linux checkouts and CI kept serving the lowercase file, and every subsequent `dkk update` on a case-insensitive machine re-did the same invisible rename forever.
- **The validating hooks blocked on their own failures.** `stop-validate.mjs` returned exit 2 for any non-zero status from `dkk validate`, which Claude Code feeds back as "Domain validation failed — fix these before ending the turn." But dkk requires Node >= 21.2, and a Stop hook under nvm/asdf is easily handed an older one, where `import.meta.dirname` throws `ERR_INVALID_ARG_TYPE`. The agent cannot fix its own toolchain, so it tries, fails, and the hook re-fires — wedging the session.

## Decision

**Record what DKK writes, and treat anything else as the user's.**

`dkk init` and `dkk update` write `.dkk/artifacts.lock`: a version-stamped JSON map of repo-relative path → sha256 of the content DKK installed. It is committed, so teammates and CI share the same provenance.

The diff becomes four-way instead of three-way:

| On disk | Class | Behaviour |
|---------|-------|-----------|
| Absent | `+ add` | Installed. |
| Matches the template | — | No change. |
| Differs from template, matches the lock | `~ replace` | Overwritten silently. |
| Differs from both | `! conflict` | **Local file kept**; template written to `<path>.new`. |

The lock is *derived*, never hand-maintained: a hash is recorded only for artifacts whose on-disk content equals the template after an install run. A conflicted file therefore never has its hash refreshed — it keeps the hash of the version DKK actually wrote, so it stays flagged until resolved, and reverting the edit restores clean-overwrite status. Failing in that direction is the safe one.

Supporting decisions:

- **Diffing is per-file, not per-directory.** Skills were previously compared as whole directories, which cannot say *which* file was edited.
- **`--diff`** renders a unified diff (dependency-free LCS, in `shared/unified-diff.ts`) for every replace and conflict, and **all decision-relevant output — including a non-mutating preview of the settings prune — moves ahead of the confirmation prompt.**
- **`--force`** opts back into overwriting, labelling those entries `OVERWRITE` and stating that local changes will be destroyed.
- **Case-only renames go through `git mv -f`** when the stale entry is tracked, which is the one operation that records such a rename under `core.ignorecase`. Untracked files fall back to a filesystem rename; a tracked file whose `git mv` fails is reported with the exact command to run by hand, rather than shipping a rename that silently does not exist.
- **Both validating hooks gate exit 2 on the validator having produced a parseable report**, not on its exit status. A report means the domain model is broken and the agent should fix it. No report means the toolchain is broken; that exits 1 — surfaced to the human, non-blocking for the agent — and names the Node version requirement, since that is the usual cause.

Rejected: marking a managed region inside the hook scripts (`// dkk:managed-start/end`) so the tail could be customised across upgrades. It solves a narrower problem than the lock at higher cost, and hook logic lives inside an event handler where a tail extension point buys little. The `.new` merge-candidate protocol — the same shape as `rpmnew`/`dpkg-dist` — covers the general case for every artifact type, not just hooks.

## Consequences

**Easier.** Customising a DKK artifact is now safe: an upgrade preserves it and hands you the new template to merge. `--diff` makes the y/N prompt a real decision. `dkk artifacts check` gains two CI-visible classes — `conflict` and `miscased` — and the latter catches exactly the drift that is invisible to `git status` on a developer's Mac. A crashed validator no longer wedges an agent session.

**Harder.** One more committed file to understand, and a stale `.dkk/artifacts.lock` (hand-edited, or lost in a bad merge) degrades conflict detection. Mitigated by treating an unreadable or future-versioned lock as *absent* rather than trusting it: those repos fall back to the old `replace`-everything behaviour and say so explicitly, rather than quietly guessing. Repos installed before 0.8.0 get that same honest degradation on their first upgrade, and acquire a lock in the process — including zero-drift repos, since the lock is rewritten even when the diff is empty.

**Ongoing.** `.new` files are DKK-written but are not managed artifacts; every scan must skip them, or the next run would sweep away the merge candidate the user still needs. That exclusion is a standing invariant of the artifact scanner.
