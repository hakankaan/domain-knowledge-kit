# ADR-0005 — Capture DKK feedback in the consuming repo

**Status:** Accepted  
**Date:** 2026-07-27  
**Deciders:** Kaan Akın

## Context

DKK ships into other people's repositories and is used almost entirely from inside an AI coding session. When it misbehaves — a confusing error, a command that half-worked, a capability that turns out not to exist — the friction is felt mid-task. Filing a GitHub issue means breaking flow, reconstructing what happened, and leaving the editor, so in practice it never happens. The maintainers only ever hear the small fraction of problems that survive until someone has spare attention.

Before this change there was no path at all:

- No feedback, telemetry, analytics, or issue-reporting mechanism anywhere in the codebase.
- No `CONTRIBUTING.md` and no issue templates.
- `package.json`'s `bugs.url` was the only pointer to the tracker, and it appeared in neither the README nor any doc — reachable only via `npm bugs`.

Meanwhile the agent in the session already holds exactly what a maintainer needs: the invocation that failed, the actual error output, and the shape of the pack it was operating on. The reporting cost is not knowledge, it is transcription and context-switching.

Four questions required resolution:

1. **Where does a note live**, given that DKK has never written anything outside `.dkk/` that the user did not ask for, and has never made a network call?
2. **What may DKK capture automatically**, given that the destination is a public issue tracker and the source is a third party's private repository?
3. **How does an agent record one**, given that the MCP server is read-only by convention and every mutation in DKK goes through the CLI?
4. **How does a note reach the maintainers** without DKK transmitting anything?

## Decision

Add a `dkk feedback` command group that records notes about **dkk itself** into `.dkk/feedback.yml` in the consuming repo, and exports them as a Markdown report a human chooses to share.

```
dkk feedback add "<summary>" [--kind bug|friction|idea|docs] [--detail …] [--command …]
dkk feedback                 # = list (default subcommand)
dkk feedback export          # Markdown on stdout, framing on stderr
dkk feedback rm <id…>
```

### 1. A committed local file, and no network egress whatsoever

Notes go to `.dkk/feedback.yml` — hand-editable YAML with a `#` header explaining what it is and inviting redaction, following the `.dkk/drift.yml` precedent. It is committed, not gitignored: feedback is a team artifact, one export should carry everything the team hit, and a note that vanishes on a fresh clone is a note that was never worth writing.

DKK makes no HTTP calls, and this feature adds none. `export` writes to stdout; a human pastes it. The tradeoff is accepted deliberately: an upload would collect vastly more feedback, and would also be the first time DKK sent a user's data anywhere — a property this project should not spend.

### 2. Auto-context is counts-only, and names are never recorded

Each entry captures `dkk` version, Node version, platform, and a best-effort agent label (`claude-code` / `copilot` / `unknown`), plus **pack size as counts**: contexts, items, ADRs, actors, flows, and whether federation is configured with how many peers. Together these answer the two questions that decide whether a bug reproduces — "which build?" and "how big is the model?" — and none of them identifies anyone.

**A context, item, actor, ADR, or flow name is never recorded.** Those names *are* the user's confidential business domain, and this file is destined for a public tracker. This is a decision, not an implementation detail: the counts-only rule is enforced by an explicit privacy assertion in `src/features/feedback/tests/feedback.test.ts` so that a later contributor cannot "helpfully" add context names.

Also deliberately excluded: repo name, git remote, branch, SHA, `cwd`, absolute paths, hostname, username, and any wall-clock time (dates are `YYYY-MM-DD`, so working hours are not disclosed). Install mode is excluded for a different reason — `detectInstallMode()` shells out to `npm root -g` with a 10-second timeout, and a command whose premise is "record it before the thought evaporates" cannot afford that.

There is deliberately **no secret scanner** over `--detail`. A scanner that misses one token is worse than none, because it manufactures confidence. The guards are instead: a file header inviting redaction, an explicit review reminder on every `export`, `dkk feedback rm` as an escape hatch, and prompt files that instruct the agent to show the draft and check it before recording.

### 3. CLI-only — the MCP server stays read-only

No `dkk_feedback` MCP tool. Mutations in DKK go through the CLI and the MCP server exposes only the read/query surface; that invariant is asserted in the server header, in the agent contract (`Mutations — CLI only (MCP is read-only)`), in `docs/ai-agent-integration.md`, and in the `dkk-domain-reviewer` subagent. Convenience here is not worth the first exception. Agents shell out, gated by a `Bash(dkk feedback:*)` entry in the bundled `.claude/settings.json`.

A read-only `dkk_feedback_list` tool was also rejected: no agent has a reason to enumerate a human's private notes about the tool.

The agent-facing surface is instead two prompt files — `/dkk-feedback` (capture) and `/dkk-feedback-export` (share), with Copilot mirrors — plus two lines in `primeContent()`: one table row so the capability is visible at all, and one constraint sentence (*"offer it, never file feedback unprompted"*) so an agent that fumbles a flag does not pollute a third party's git history. No skill: skills are listed in every session's context, and a slash command plus one line is the whole workflow.

### 4. `export` is an artifact on stdout, and read-only by default

The Markdown goes to **stdout** and every hint goes to **stderr**, so `| pbcopy`, `> report.md`, and `gh issue create --body-file -` all receive clean Markdown. This deviates from the other commands (which print everything to stdout) because the export *is* an artifact rather than a report about one.

`export` does not mutate unless `--mark-shared` is passed. A command intended to be piped must be idempotent, or `| head` silently changes state.

Only a **title** is ever prefilled into an issue URL, and only for a single-entry export. URL-encoding Markdown roughly triples its length, so a prefilled `body` would silently truncate the tail of a multi-entry bug report — the worst available failure mode. Bodies travel by paste or `--body-file -`.

### 5. Unparseable is an error; partially-malformed refuses to be written over

`.dkk/drift.yml` warns and continues when it cannot be parsed, because its contents are recomputable. `.dkk/feedback.yml` holds the only copy of something a human wrote, so the asymmetry is inverted on purpose:

- **Unparseable YAML** → error, exit 1. Treating it as an empty log would look exactly like the captured feedback having evaporated.
- **Parseable but wrong-shaped** → drop the unusable entries, warn, and continue for *read* commands.
- **Any command that writes**, when normalisation dropped anything → refuse to save. Normalise-then-save is silent data loss.

Unknown entry keys survive a load→save round trip, so a file written by a newer dkk is not shredded by an older one.

## Consequences

### Positive

- **Feedback gets captured at the moment of friction**, by the participant who already knows what failed, at a cost of one confirmation.
- **Reports arrive reproducible.** Version, platform, and pack size are attached without anyone remembering to include them.
- **The privacy posture is explicit and testable** rather than implicit. "No network calls" remains true of DKK as a whole.
- **The project finally has a stated feedback path.** README, `docs/cli-reference.md`, and `docs/ai-agent-integration.md` now point at the issue tracker, which previously existed only in `package.json`.
- **No new plumbing.** The prompt files are adopted by `dkk update` automatically (the artifact inventory walks the template dirs), and the permission entry flows through the existing additive settings merge.

### Negative

- **Feedback still only moves when a human moves it.** Most notes will never be exported. Accepted: the alternative is transmitting a user's data.
- **Meta-noise in someone else's repo.** `.dkk/feedback.yml` is committed, so notes about dkk appear in a team's history and diffs alongside their own work.
- **Concurrent appends conflict.** Two developers appending produce one merge hunk and can both claim the same `fb-NNNN`. Mitigated rather than solved: ids are display-only, `nextFeedbackId` is max+1 so a duplicate self-heals on the next `add`, `rm` refuses an ambiguous id with a "likely a merge" message, and `.gitattributes merge=union` is documented as an optional team tip. DKK does not write a consumer's `.gitattributes`.
- **Agents may over-file.** An LLM that learns the command exists may reach for it whenever anything goes wrong. Mitigated by the "never unprompted" instruction, the slash command being the primary path, and entries landing in `git status` where the user sees them before committing. No throttling — accepted residual risk.
- **One more surface to keep in sync.** The two Claude commands, two Copilot prompts, `primeContent()`, `GUIDE_CLI`, and `init.ts#dkkSection` must move together when the command changes.

### Neutral

- `.dkk/feedback.yml` has no JSON Schema and is invisible to the loader and validator. A malformed feedback file must never fail a consumer's CI gate; an integration test pins that `dkk validate` ignores it.
- The file carries `version: 1`, giving a future migration something to branch on — insurance `.dkk/drift.yml` does not have.
- `list` is the default subcommand, so a bare `dkk feedback` reads rather than writes, and the empty state carries the onboarding copy (the same pattern as `dkk drift`'s unadopted-feature branch).

## Alternatives Considered

- **Anonymous telemetry uploaded to a maintainer endpoint.** Rejected: it would collect far more, but it makes DKK the first thing in this project to send a user's data anywhere, requires infrastructure the project has deliberately avoided (see ADR-0003's "no new infrastructure" constraint), and demands a privacy policy and an opt-out for a tool that currently needs neither.
- **A prefilled `issues/new?title=&body=…` URL.** Rejected: encoded Markdown blows past reliable URL length limits at roughly two entries, and truncation is silent — it would eat the end of a bug report with no signal. Only the title is prefilled, and only for a single entry.
- **Emitting a `gh issue create` command as the primary path.** Rejected as the *primary* path (useless without `gh` installed and authenticated), but printed on stderr as a secondary one, since it is the path an agent will take and `--body-file -` has no length limit.
- **Gitignoring `.dkk/feedback.yml`.** Rejected: it removes the merge-conflict problem, but feedback becomes per-developer and per-clone, and the maintainer receives one person's fragment instead of the team's.
- **One file per entry (`.dkk/feedback/fb-0001.yml`).** Rejected: it eliminates conflicts entirely, but a single hand-editable, hand-redactable file is the whole premise — a user must be able to read everything they are about to share in one place — and `export` has to read all of them anyway.
- **A `dkk_feedback` MCP write tool.** Rejected: see decision 3. The read-only invariant is worth more than saving the agent a shell-out.
- **A skill instead of prompt files.** Rejected: ADR-0002 chose skills for workflows that encode reusable behavioural judgement. Recording a note is not that, and skills cost context in every session whether used or not.
