# ADR-0003 — Multi-Repo Federation

**Status:** Accepted
**Date:** 2026-05-13
**Deciders:** Kaan Akın

## Context

DKK was originally single-repo: `loadDomainModel` walked one `.dkk/` rooted at `process.cwd()` and built one in-memory `DomainModel`. All cross-references used the grammar `<context>.<Name>` and resolved only inside that single tree.

This is a poor fit for enterprise architectures where each service lives in its own repository. Specifically:

1. **AI assistants are blind across the boundary.** A developer working in `billing-svc` cannot ask Claude "what fields does `ordering:OrderPlaced` carry?" because the agent has no way to load `order-svc`'s domain model.
2. **Cross-service references don't validate.** A policy in `billing-svc` that reacts to an event in `order-svc` gets flagged as a dangling ref because the producer's items aren't in scope.
3. **Producers can't see consumers.** When `order-svc` renames an event, no tooling answers "who depends on this?".
4. **Org-wide visibility is manual.** Architects and PMs have no rendered view of how `payments → ordering → fulfillment` actually wire together.

A workable solution had to satisfy several constraints from real-world enterprise usage:

- **No CI requirement.** Adding federation must not force every consumer team to set up a publish pipeline. The peer's raw `.dkk/` directory should be the artifact.
- **No new infrastructure.** No hub daemon, no central registry, no shared service to host.
- **Mixed source types.** Some peers will be checked out locally (inner dev loop); others will be referenced remotely via git URL + branch (CI, onboarding).
- **Backward compatibility.** Repos that don't adopt federation must keep working unchanged. The ref grammar must be additive — bare `<context>.<Name>` continues to mean "local".
- **AI-first.** The primary user experience is a developer asking their AI assistant cross-service questions, so MCP and reading commands must transparently span peers.

## Decision

Adopt a federation layer with the following design:

### 1. Service identity (`.dkk/service.yml`)

Each repo opts into federation by declaring itself as a service:

```yaml
name: ordering          # globally unique, kebab-case
exports:                # bounded contexts this service publishes
  - ordering
description: Customer order lifecycle.
```

Service identity is optional: legacy repos without `service.yml` keep working exactly as before (`model.service === undefined`).

### 2. Federation manifest (`.dkk/federation.yml`)

A repo lists peer services explicitly:

```yaml
peers:
  - name: ordering
    source:
      type: local
      path: ../order-svc            # absolute or repo-root-relative
  - name: payments
    source:
      type: git
      url: git@github.com:acme/payments-svc.git
      branch: main
      path: services/payments        # optional, for monorepo peers
```

Two source types are supported; both are first-class:

- **`local`** — the loader reads `<path>/.dkk/` directly on every command. No fetch step, always live. Ideal for the inner dev loop.
- **`git`** — `dkk pull` performs a depth-1 + blobless + sparse-checkout of just `.dkk/` into `.dkk/imports/<service>/`. Resolved commit SHAs are pinned in `.dkk/federation.lock.json` (committed) so two developers see the same peer state until someone re-pulls.

A `DKK_PEER_<NAME>` env var overrides any peer's resolved path, giving per-developer redirection without diverging the committed manifest.

### 3. Cross-service reference grammar

Bare refs (`<context>.<Item>`, `actor.X`, `adr-NNNN`, `flow.X`, `context.X`) keep their existing semantics — they resolve only against the local repo. A new optional `<service>:` prefix federates any of these forms:

| Bare form | Federated form |
|---|---|
| `ordering.OrderPlaced` | `ordering:ordering.OrderPlaced` |
| `actor.PaymentGateway` | `payments:actor.PaymentGateway` |
| `adr-0001` | `ordering:adr-0001` |
| `flow.OrderFulfillment` | `ordering:flow.OrderFulfillment` |
| `context.ordering` | `ordering:context.ordering` |

A self-prefix (`<localService>:<id>` inside the local service) resolves locally — the validator strips the prefix before lookup. This is purely additive: every existing repo's YAML continues to validate without churn.

### 4. Loader semantics

The shared `loadDomainModel` builds the local `DomainModel` exactly as before, then a federation hook (registered by the federation slice at module-init time) hydrates `model.peers: Map<string, DomainModel>` from each reachable peer. The peer's model is structurally identical to a local model — peers are loaded with the same `loadDomainModel`, but with `followPeers: false` so transitivity is forbidden (one level deep, no peer-of-peer).

Unreachable peers degrade to **warnings** by default; `dkk validate --federation strict` escalates them to errors for CI gates. Peer YAML using DKK schema fields the local DKK version doesn't recognise is loaded in lenient mode so cross-version drift doesn't break the consumer.

### 5. Validator: parallel index sets, never fall through

The cross-reference phase builds two independent lookup tiers: local sets (unchanged) plus per-service peer sets (`peerDomainItemIds`, `peerAdrIds`, `peerExports`). The routing rule is strict: a **bare** ref resolves only against local; a **service-prefixed** ref resolves only against the named peer. There is no fall-through. This rules out an entire class of silent data-corruption bugs where two services with the same item name would accidentally cross-resolve.

### 6. No hub, no publish step

Two alternatives were considered and rejected:

- **A `dkk publish` artifact** (JSON pack, orphan branch, OCI registry) — adds friction, requires CI on every producer, doesn't help the inner dev loop where peers are checked out locally.
- **A hub daemon** (hosted MCP endpoint, web UI, central reverse index) — adds infra (hosting, auth, on-call) for benefits that mostly arrive only at large scale (~30+ services).

Instead the org-view repo pattern is the documented recipe: one repo with no domain of its own, just a `federation.yml` listing every service, rendered on a schedule. Zero new code. If a hosted hub ever becomes necessary, it's a thin daemon over the org-view repo — same data, just a network access mode.

### 7. Read paths span peers transparently

- **Indexer** namespaces peer rows with `<service>:` prefix and adds a `service` column. Search filters via `--service`.
- **Graph** walks each peer model with a service-prefix wrapper around `ensureNode`. Cross-service edges are traversable by BFS.
- **`dkk show <service>:<id>`** resolves against `model.peers.get(<service>)` and labels the result `[peer: <name>]`.
- **MCP server** — existing tools (`dkk_search`, `dkk_show`, `dkk_related`, `dkk_summary`, `dkk_list`, `dkk_locate`) become transparently federated. Two new tools added: `dkk_peers` (status), `dkk_consumers` (reverse-lookup).
- **`dkk consumers <id>`** — new CLI/MCP command that walks every loaded peer and reports references back to a local item. The producer-side answer to "who breaks if I rename this?".

### 8. Walk-up `repoRoot()`

To support monorepos where services live under `services/<name>/`, `repoRoot()` now walks up from `cwd` to the nearest ancestor containing `.dkk/`. Disabled with `DKK_DISABLE_WALKUP=1`; explicit `--root` always wins. The walk-up is exposed as a standalone `findDkkRoot(from)` helper for other tools.

## Consequences

### Positive

- **Cross-repo AI experience works** without any CI, publish step, or shared infrastructure. The MCP server in `billing-svc` answers questions about `order-svc`'s items as long as the peer is locally checked out or git-pulled.
- **Backward compatible** — every existing repo keeps working with zero changes. Federation is opt-in via the presence of `.dkk/service.yml` and `.dkk/federation.yml`.
- **Composable across source types** — `local:` for the inner dev loop, `git:` for CI and onboarding, env-var override for per-developer redirection.
- **Reverse-lookup answers the rename safety question** for producers via `dkk consumers`.
- **Org-view pattern is just a usage of existing tooling**, not a new product.

### Negative

- **Discovery is opt-in.** A new dev joining `billing-svc` doesn't automatically know which peers to add — they read `federation.yml` and follow what's there. There's no org-wide registry today (the org-view repo recipe is the substitute).
- **Schema drift is bounded but real.** Peers using newer DKK schema fields are loaded leniently, but the consumer's tooling can't act on fields it doesn't understand. Cross-version compatibility is the producer's responsibility.
- **Peer authentication is the user's problem.** `dkk pull` shells to `git`; SSH keys or credential helpers must already be configured. No token storage, no GitHub App.
- **One-level-deep loading means transitive consumers must declare every direct producer.** A `billing` repo that depends on `ordering` (which depends on `inventory`) must list `inventory` in its own manifest if it wants to reference `inventory:*` items. By design — keeps loading deterministic and avoids transitive explosion.

### Neutral

- **The federation slice owns its complexity.** The shared loader knows nothing about peers beyond an opt-in hook; removing federation in the future is a single-file deletion.
- **`<service>:` is purely additive.** Tooling that doesn't know about federation (e.g. older versions of this CLI) sees ref strings as unrecognised but still well-formed.
- **Lock file is committed; cache is gitignored.** Reproducibility for shared CI without the bulk of cached `.dkk/` trees.

## Implementation phases

1. **Identity + ref grammar** — `service.yml` schema, `parseRef`, walk-up `repoRoot`. Additive, no peers yet.
2. **Local-path peers** — federation manifest, peer loader, `dkk peers add|list|status`, `dkk show <service>:<id>`. This phase alone delivers the inner dev loop.
3. **Git-path peers** — `dkk pull`, sparse-checkout fetcher, lockfile, `--refresh` / `--offline`.
4. **Cross-service validation** — schema regex relaxation, validator parallel peer sets, `--federation strict`.
5. **Federated reads + reverse-lookup** — graph peer walks, indexer service column, MCP tool updates, `dkk consumers`.

## Out of scope (deferred)

- Hub daemon / hosted MCP endpoint. Org-view repo recipe is the substitute.
- A `.dkk/federation.local.yml` per-developer overlay. Env-var overrides handle the same use case.
- Contract / structural-hash drift detection (e.g. "payments shipped v2 of `PaymentCaptured`, your reference is still on v1"). Achievable as a periodic `dkk pull && dkk validate` CI job on the consumer side; no structural hash in MVP.
- Transitive peer-of-peer loading. Hard cap at one level; consumers must declare every direct producer.
- A `dkk peers scan <dir>` auto-wire for monorepos / sibling-directory clones. Worth adding later; not in scope.
